# maclm-agent — Техническая спецификация

**Revision 3** · macOS 15 Sequoia+ · Apple Silicon
**Изменения Rev 3:** переработан раздел 6 (модель безопасности: уровни риска, правила, аудит), добавлен раздел 9 (системная интеграция), обновлён раздел 10 под новый порядок фаз.

---

## 1. Обзор

`maclm-agent` — нативный AI-ассистент для macOS, работающий полностью офлайн через локально хостируемую LLM. Никаких облачных зависимостей, никакой телеметрии, никаких ключей от внешних сервисов.

**Стек:** Swift 6, SwiftUI, SwiftData
**Минимальная цель:** macOS 15 Sequoia, Apple Silicon
**Провайдеры LLM:** LM Studio, Ollama (в перспективе — MLX)
**Распространение:** прямое, ad-hoc подписанный DMG через GitHub Releases. Без App Store, без sandbox-энтайтлмента, без нотаризации (с возможностью перейти на неё позже).

### 1.1 Принципы

1. **Каждый этап = работающий продукт.** Ни один шаг не оставляет приложение в нерабочем состоянии.
2. **Локальность по умолчанию.** Автоопределение обращается к `localhost`; ручная настройка допускает произвольный HTTP(S)-сервер. Ограничение только loopback в текущем коде не принуждается.
3. **Человек в контуре.** Ни одно потенциально разрушительное действие не выполняется без явного подтверждения.
4. **Расширяемость через протоколы.** Провайдеры и инструменты добавляются без переписывания ядра.

## 2. Архитектура

Фактические каталоги находятся внутри `maclm-agent/`:

```
App/            MacLMAgentApp, Window + Settings, AppKit menu bar и пикер
Core/           AgentLoop, ChatViewModel, ProviderCoordinator, настройки и Clipboard Actions
LLM/            LLMProvider, LMStudioProvider / OllamaProvider, discovery и парсеры
Tools/          Tool, ToolRegistry, семь реализаций инструментов
Security/       ConfirmationCoordinator и AccessibilityPermissionService
Persistence/    Conversation, Message, ToolCall, ClipboardAction, store и KeychainService
UI/             представления чата, настроек, пикера, редакторов
```

Отдельного каталога `Clipboard/`, `AppState` и явного плана миграций нет. Правила, новые уровни риска и аудит планируются в v0.3 (раздел 6).

### 2.1 Два режима одновременно

SwiftUI `Window` и AppKit `MenuBarController` (`NSStatusItem` + `NSPopover` с `NSHostingController`) делят один `ChatViewModel` (`@MainActor`, `@Observable`), `AppSettings` и контейнер SwiftData. Переключение между ними сохраняет активную беседу и стриминг.

### 2.2 Агентный цикл

Пользовательское сообщение → запрос к провайдеру → стриминг токенов → при наличии `tool_calls` цикл прерывается, вызовы проходят через слой безопасности, результаты возвращаются в историю, цикл повторяется до ответа без вызовов.

`AgentLoop` по умолчанию ограничен восемью итерациями. Вызовы выполняются последовательно после получения полного ответа провайдера; фрагменты аргументов накапливаются до выполнения.

## 3. Модель данных (SwiftData)

| Модель | Фактические поля и связи |
|---|---|
| `Conversation` | `id`, `title`, `createdAt`, `updatedAt`, `messages` (cascade); провайдер и модель в беседе не хранятся |
| `Message` | `id`, `roleRawValue` (вычисляемый `role`), `content`, `toolCallID`, `timestamp`, `conversation`, `toolCalls` (cascade) |
| `ToolCall` | `id`, `providerCallID`, `toolName`, `argumentsJSON`, `resultJSON`, `statusRawValue` (вычисляемый `status`), `timestamp`, `message` |
| `ClipboardAction` | `id`, `name`, `promptTemplate`, `iconSystemName`, `sortOrder`, `isEnabled`, `isBuiltIn`, `createdAt`, `updatedAt` |

Статусы `ToolCallStatus`: `pending`, `approved`, `rejected`, `completed`, `failed`. Отдельное поле решения не хранится: статус меняется по мере выполнения, поэтому успешный вызов заканчивается `completed`.

Контейнер регистрирует только эти четыре модели. `SecurityRule` и `AuditEntry` ещё не реализованы; их проектная схема — в 6.3 и 6.5. Настройки и глобальный выбор провайдера/модели — `UserDefaults`; сервис секретов — `KeychainService`.

## 4. LLM-слой

### 4.1 Протокол

```swift
protocol LLMProvider: Sendable {
    var name: String { get }
    func streamChat(
        messages: [ChatMessage],
        tools: [ToolDefinition]
    ) -> AsyncThrowingStream<ChatStreamEvent, Error>
}
```

`ChatStreamEvent`: `contentDelta(String)`, `toolCallDelta(ToolCallDelta)`, `done`. Ошибки завершают throwing stream. Модели перечисляет отдельный `ProviderDiscovery` как `[String]`; выбранная модель передаётся в конструктор провайдера.

### 4.2 Реализации

- **LM Studio** — OpenAI-совместимый эндпоинт, порт 1234 по умолчанию.
- **Ollama** — нативный API, порт 11434 по умолчанию.

Автоопределение по порту при старте; ручной выбор провайдера и адреса в настройках перекрывает автодетект.

### 4.3 Function calling

LM Studio использует OpenAI-совместимый tool calling и SSE; Ollama — нативный `/api/chat` и NDJSON. Схемы формируются из `ToolRegistry`. `AgentLoop` всегда передаёт определения инструментов: проверки поддержки tool calling моделью и автоматического режима без инструментов нет. Текстового фолбэк-протокола нет.

## 5. Инструменты

### 5.1 Протокол

Текущий протокол (планируемые изменения безопасности описаны в разделе 6):

```swift
protocol Tool: Sendable {
    var name: String { get }
    var description: String { get }
    var parametersSchema: JSONSchema { get }
    var riskLevel: RiskLevel { get }
    func execute(arguments: [String: Any]) async throws -> ToolExecutionResult
}
```

### 5.2 Текущий набор (v0.2.4)

| Инструмент | Текущий `riskLevel` |
|---|---|
| `read_file` | safe |
| `list_dir` | safe |
| `search_files` | safe |
| `write_file` | confirm |
| `move_file` | confirm |
| `delete_file` | confirm |
| `run_shell` | confirm |

`RiskLevel` сейчас содержит `safe`, `confirm`, `deny`; все уровни, кроме `safe`, проходят подтверждение в `AgentLoop`. Самостоятельной блокировки для `deny` нет. Повышение по аргументам отсутствует. Три новых уровня — план v0.3.

`delete_file` перемещает объект в Корзину. `run_shell` уже зарегистрирован в `ToolRegistry.all`: выполняет точную команду через `/bin/zsh -c`, возвращает stdout/stderr, exit code и признак таймаута (по умолчанию 30 секунд), поддерживает отмену. Потокового вывода в чат, direct-режима и явной рабочей директории пока нет.

## 6. Модель безопасности (реализовано в v0.3.4; будущие номера Rev 3)

### 6.1 Уровни риска

```swift
enum RiskLevel: Int, Comparable {
    case safe       // выполняется без подтверждения
    case caution    // подтверждение, допустима сессионная память
    case dangerous  // подтверждение всегда, память не применяется
}
```

**Определение уровня:** статичный базовый уровень объявляется инструментом; конкретный вызов может быть **повышен** на основании аргументов. Понижение невозможно ни при каких условиях.

Примеры повышения:
- `write_file` вне `allowed_dirs` → `dangerous`
- `delete_file` по пути с wildcard или на директорию → `dangerous`
- shell-команда в режиме `shell` (`/bin/zsh -c`) → всегда `dangerous`, независимо от содержимого (v0.4)

### 6.2 Подтверждение

Карточка Approve/Reject в ленте чата, визуально различающаяся по уровню: цвет рамки и заголовка, для `dangerous` — аргументы всегда развёрнуты, без сворачивания.

**Сессионная память** — только для `caution`. Пользователь может отметить «не спрашивать в этой сессии» — правило действует на пару (инструмент, уровень) до перезапуска приложения. Для `dangerous` опция недоступна: каждое обращение требует отдельного подтверждения. Это сознательное решение — иначе одно рассеянное нажатие открывает инструменту доступ на всю сессию.

### 6.3 Правила allow/block

Схема хранит четыре измерения. Сейчас принуждение включено только по `path` для шести файловых инструментов; остальные измерения всегда возвращают «нет решения». Будущие номера в таблице сохранены по Rev 3 до шага 4.pre:

| Измерение | Что описывает | Принуждение с |
|---|---|---|
| `path` | пути и глобы файловой системы | **v0.3** |
| `command` | regex-паттерны shell-команд | v0.4 |
| `application` | bundle ID целевых приложений | v0.5 |
| `host` | сетевые хосты | best effort, без гарантий |

```swift
@Model final class SecurityRule {
    var dimension: RuleDimension   // path | command | application | host
    var pattern: String
    var action: RuleAction         // allow | block
    var isEnabled: Bool
    var order: Int
    var isBuiltIn: Bool
    var ruleDescription: String
    var createdAt: Date
}
```

**Порядок разрешения:** включённые правила сортируются по `order`, затем `createdAt` и паттерну. Первое совпавшее block имеет безусловный приоритет над любым allow; порядок существенен между правилами одного действия. Разные измерения не конкурируют. При отсутствии совпадений — поведение по умолчанию для уровня риска. Allow не понижает риск.

Пути канонизируются с раскрытием `~`, существующих symlink и `..`; проверяются и исходный путь, и нормализованный аргумент инструмента. Совпадение с предком распространяется на потомков. Глобы поддерживают только `*`, `**`, `?`; List/Search фильтруют запрещённых потомков.

Редактор группирует правила по четырём измерениям, валидирует паттерны, сохраняет порядок перетаскивания и показывает решение всего набора на примере, включая несохранённый вариант. Встроенные правила можно только включать/выключать. Сброс с подтверждением восстанавливает все 16 встроенных правил и не меняет пользовательские. Набор загружается из SwiftData перед каждым вызовом; изменения действуют со следующего вызова без перезапуска.

**Про сетевые хосты — честно.** Статический анализ аргументов не может определить, куда пойдёт `npm install`, `git pull` или произвольный скрипт. Будущая проверка ограничится явными URL в аргументах; в v0.3.4 `host` только сохраняется. В UI это измерение помечается как неполное, чтобы не создавать ложного чувства защиты. Настоящее ограничение сети потребовало бы прокси или sandbox-профиля — вне текущего scope.

### 6.4 Sandbox-режим

**Не реализуется.** Списки правил — механизм фильтрации структурированных целей; граница применимости и роль подтверждения для универсальных инструментов описаны в 6.6. Отдельный режим со своей семантикой создавал бы вторую, конкурирующую модель разрешений, которую пришлось бы держать согласованной с первой.

### 6.5 Журнал аудита

Каждый вызов инструмента фиксируется независимо от исхода:

```swift
@Model final class AuditEntry {
    var timestamp: Date
    var toolName: String
    var argumentsJSON: String
    var riskRaw: Int            // вычисляемый riskLevel: RiskLevel
    var elevationReason: String?
    var decisionRaw: String     // вычисляемый decision: AuditDecision
    var matchedRuleDescription: String?
    // decision: AuditDecision        // approved | rejected | auto | blocked
    var outcome: AuditOutcome     // success | failure | cancelled | notExecuted
    var resultSummary: String
    var errorDescription: String?
    var durationMilliseconds: Int?
    var conversationID: UUID?
}
```

Хранение — SwiftData. Просмотр — отдельное окно с фильтрами по дате, инструменту, уровню и решению. Экспорт — JSONL-файл на диск. Аргументы и summaries ограничены по длине, но не маскируются по содержимому; содержимое успешно прочитанных файлов в summary не копируется. Команды, write_file content и shell stdout/stderr могут содержать секреты. Срок хранения — 30/90/365 дней или бессрочно, очистка старых записей при запуске; ручная очистка требует подтверждения.


### 6.6 Классы инструментов и граница применимости политик

Инструменты делятся на два класса по одному признаку: можно ли к их аргументам детерминированно применить политику безопасности.

**Структурированные** (`isPolicyEnforceable = true`). Аргументы типизированы, объекты воздействия (пути, хосты, bundle ID) извлекаются из аргументов без интерпретации кода. Сюда относятся файловые инструменты (v0.1) и инструменты Native API (v0.6). Для них действует вся модель: базовые уровни, повышение по аргументам, allow/block-правила, сессионная память для `caution`.

**Универсальные** (`isPolicyEnforceable = false`). Аргумент — произвольный код или командная строка, из которых нельзя надёжно определить, что будет затронуто. Сюда относятся `shell`-режим Shell-инструмента (v0.4) и AppleScript / Apple Events (v0.5). Правила для них:
- эффективный уровень риска всегда `dangerous`, независимо от объявленного базового уровня; сессионной памяти нет;
- карточка подтверждения показывает полный текст команды или скрипта;
- allow/block-правила могут применяться как дополнительный фильтр запрета там, где цель извлекается (например, `tell application` для измерения `application`), но никогда не понижают уровень риска.

**Fail-closed по умолчанию.** Значение `isPolicyEnforceable` по умолчанию в протоколе — `false`. Инструмент, не объявивший свой класс явно, считается универсальным и всегда требует подтверждения.

**Direct-режим Shell** (`Process` с массивом аргументов) — открытый вопрос v0.4: исполняемый файл извлекается детерминированно, но семантика аргументов зависит от программы. Решается в разборе v0.4.

**Текущий `run_shell`.** Выполнение через `/bin/zsh -c`, таймаут по умолчанию 30 секунд, отмена, карточка и аудит уже реализованы. Правила по путям к нему не применяются: запрет `~/.ssh/**` не остановит `cat ~/.ssh/id_rsa`. В редакторе это постоянное предупреждение. Direct-режим пока отсутствует.

**Граница безопасности.** Sandbox-режима нет, поэтому allow/block-правила защищают от ошибок модели и неудачных формулировок, но не от скомпрометированной модели (prompt injection через содержимое файлов, буфера обмена, документов). Как только в реестре есть хотя бы один универсальный инструмент, правила по путям перестают быть границей: то же действие достижимо через `do shell script` или Finder. Границей безопасности в этом случае является подтверждение человеком каждого `dangerous`-вызова. Документация и интерфейс не должны обещать большего.

**Маршрутизация возможностей.** Для каждой возможности существует один канонический инструмент. Файловые операции выполняются только файловыми инструментами. Описания Shell- и AppleScript-инструментов прямо указывают модели не использовать их для чтения, записи, перемещения и удаления файлов. AppleScript предназначен для управления приложениями: Mail, Calendar, специфичные для Finder действия (теги, Reveal, Корзина).

**AppleScript (v0.5), предварительные требования:**
- цели `tell application` проверяются по измерению `application`;
- наличие `do shell script` в скрипте дополнительно подчиняет вызов правилам измерения `command`;
- если цели скрипта извлечь не удалось, это отражается в причине уровня на карточке подтверждения.

## 9. Системная интеграция (Rev 3, планируется)

### 9.1 Shell / Terminal (v0.4)

Выполнение команд через `Process` с потоковым выводом stdout/stderr в ленту чата, таймаутами, отменой и явной рабочей директорией.

**Два режима запуска**, объявляемых параметром вызова:

| Режим | Реализация | Уровень риска |
|---|---|---|
| `direct` | `executableURL` + `arguments` | базовый, повышение по аргументам |
| `shell` | `/bin/zsh -c "строка"` | **всегда `dangerous`** |

Режим `shell` даёт пайпы, подстановки и `&&` — вместе со всем, чего модель не имела в виду. Поэтому цена выбора не зависит от самооценки модели: выбор режима остаётся за ней, уровень риска выводится автоматически.

Отдельный инструмент «открыть в Terminal.app» — для интерактивных команд, вывод которых ассистент не должен перехватывать.

### 9.2 Apple Events / AppleScript (v0.5)

Выполнение через `NSAppleScript` / `osascript`, плюс готовые рецепты для Finder, Mail, Calendar, Music, Safari/Chrome, Notes, Reminders.

**Ограничение, заложенное заранее:** Apple Events требуют TCC-разрешения на автоматизацию (`NSAppleEventsUsageDescription` + энтайтлмент `com.apple.security.automation.apple-events`), выдаваемого отдельно на каждую пару «наше приложение → целевое приложение». При ad-hoc подписи идентичность бандла меняется на каждой пересборке, поэтому в разработке разрешения будут слетать постоянно — умноженно на количество целевых приложений. То же, что уже наблюдалось с Accessibility в v0.2, только шире.

### 9.3 Нативные API (v0.6)

То, для чего AppleScript избыточен: `NSWorkspace` (запуск приложений, открытие файлов и URL), системная информация (батарея, диски, сеть, память), уведомления, громкость и яркость, управление окнами через Accessibility.

## 11. Нефункциональные требования

- Первый токен ответа — не позднее 2 с после отправки при загруженной модели
- Интерфейс не блокируется во время стриминга и выполнения инструментов
- Отмена любой длительной операции доступна в любой момент
- Приложение работает при полностью отключённой сети (кроме обращений к `localhost`)
- Нет исходящего трафика за пределы `localhost` ни при каких условиях

## 12. Распространение

Ad-hoc подпись (`codesign --sign -`), DMG с drag-to-install, публикация через `gh` CLI. В README — инструкция обхода Gatekeeper (правый клик → «Открыть», либо `xattr -cr`). Переход на полную нотаризацию выполняется заменой `--sign -` на Developer ID и добавлением шагов `notarytool` / `stapler`, без изменений в коде.
