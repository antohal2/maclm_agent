## 1. Обзор

`maclm-agent` — нативный AI-ассистент для macOS, работающий полностью офлайн через локально хостируемую LLM. Никаких облачных зависимостей, никакой телеметрии, никаких ключей от внешних сервисов.

**Стек:** Swift 6, SwiftUI, SwiftData
**Минимальная цель:** macOS 15 Sequoia, Apple Silicon
**Провайдеры LLM:** LM Studio, Ollama (в перспективе — MLX)
**Распространение:** прямое, ad-hoc подписанный DMG через GitHub Releases. Без App Store, без sandbox-энтайтлмента, без нотаризации (с возможностью перейти на неё позже).

### 1.1 Принципы

1. **Каждый этап = работающий продукт.** Ни один шаг не оставляет приложение в нерабочем состоянии.
2. **Локальность по умолчанию.** Сетевая активность — только к `localhost`; другой хост возможен лишь после явного подтверждения пользователем (см. 13.8).
3. **Человек в контуре.** Ни одно потенциально разрушительное действие не выполняется без явного подтверждения.
4. **Расширяемость через протоколы.** Провайдеры и инструменты добавляются без переписывания ядра.
5. **Безопасность видима (Rev 4).** Уровень риска, действующие правила и возможность отката показываются там, где пользователь принимает решение, а не только в настройках.

## 2. Архитектура

Фактические каталоги внутри `maclm-agent/`:

```
App/            MacLMAgentApp, Window + Settings, AppKit menu bar и пикер
Core/           AgentLoop, ChatViewModel, ProviderCoordinator, настройки, Clipboard Actions
LLM/            LLMProvider, реализации провайдеров, discovery и парсеры
Tools/          Tool, ToolRegistry, семь инструментов
Security/       риск, SecurityPolicyEngine, подтверждения, SessionPermissions, редактор правил
Persistence/    SwiftData-модели, AuditMaintenance, KeychainService
UI/             чат, настройки, пикер, редакторы, журнал аудита
```

Отдельных `Clipboard/`, `Workspace/`, `Pet/` и `AppState` пока нет. Workspace, питомец и чекпоинты — план Rev 4. Контейнер создаётся в `MacLMAgentApp`; `VersionedSchema` / `SchemaMigrationPlan` отсутствуют.

### 2.1 Два режима одновременно

SwiftUI `Window` и AppKit `MenuBarController` (`NSStatusItem` + `NSPopover` с `NSHostingController`) делят один `ChatViewModel` (`@MainActor`, `@Observable`), `AppSettings` и контейнер SwiftData. Переключение сохраняет активную беседу и стриминг. `MenuBarExtra` и `WindowGroup` фактически не используются.

### 2.2 Агентный цикл

Пользовательское сообщение → стриминг провайдера → накопление полного ответа и аргументов tool calls → последовательное выполнение инструментов → результаты в историю → повтор до ответа без вызовов. По умолчанию максимум восемь итераций.

Сейчас `ChatViewModel` хранит один actor `AgentLoop` (`Core/Core.swift`) и `generationTask`. `MacLMAgentApp` создаёт и хранит общий view model; `MainWindowView` передаёт его в `ChatView`, menu bar получает тот же объект. Представление циклом не владеет. Одновременно выполняется одна генерация на приложение; смена выбранной беседы сама по себе задачу не отменяет.

Каждый вызов проходит через `AgentLoop`: загрузка правил → `ToolRiskEvaluator` → `SecurityPolicyEngine` → подтверждение / сессионная память → `Tool.execute` → аудит. Решения безопасности находятся в `Security/`, запись аудита координируется в `AgentLoop`.

**Rev 4:** цикл будет принадлежать `SessionRunner` конкретной беседы; независимые фоновые сессии описаны в 13.3.

## 3. Модель данных (SwiftData)

| Модель | Назначение |
|---|---|
| `Project` | **Rev 4.** Проект: имя, рабочая папка, инструкции, порядок |
| `Conversation` | беседа: `id`, заголовок, даты, сообщения (cascade); проект, закрепление, архив, ручной заголовок, непрочитанный результат; modelID/providerID и lastContextTokens с nil по умолчанию |

| `ToolCallRecord` | имя инструмента, аргументы, результат, providerCallID, timestamp, связь с Message; статус pending/approved/rejected/completed/failed, снимок уровня и причины для подтверждения (confirmationRiskRawValue/confirmationRiskReason). Отдельное решение пользователя не хранится |
| `ClipboardAction` | действие над буфером: имя, промпт, порядок, флаги |
| `SecurityRule` | правило allow/block (см. 6.3); **Rev 4:** необязательная привязка к проекту |
| `AuditEntry` | запись журнала вызовов (см. 6.5); **Rev 4:** ссылка на чекпоинт |

Контейнер регистрирует восемь моделей: Conversation, Project, Message, ToolCall, ClipboardAction, SecurityRule, AuditEntry, Checkpoint. Настройки — `UserDefaults`. Секреты — Keychain.

## 4. LLM-слой

### 4.1 Протокол

```swift
protocol LLMProvider {
    var identifier: String { get }
    func availableModels() async throws -> [ModelInfo]
    func stream(_ request: ChatRequest) -> AsyncThrowingStream<StreamEvent, Error>
}
```

`StreamEvent` — токен текста, начало/завершение вызова инструмента, финализация, ошибка; **Rev 4:** событие `usage` с числом токенов запроса и ответа, если провайдер его отдаёт.

Сейчас протокол только стримит сообщения и определения инструментов; список моделей получает отдельный ProviderDiscovery как [ModelInfo]. События — дельта текста, дельта tool call, usage, done; ошибки завершают throwing stream. Имена и сигнатуры сопоставлены в приложении A.

### 4.2 Реализации

- **LM Studio** — OpenAI-совместимый эндпоинт, порт 1234 по умолчанию.
- **Ollama** — нативный API, порт 11434 по умолчанию.

Автоопределение по порту при старте; ручной выбор провайдера и адреса в настройках перекрывает автодетект.

### 4.3 Function calling

Нативный OpenAI-совместимый tool calling. Схемы инструментов формируются из реестра. Сейчас AgentLoop всегда передаёт определения инструментов: проверки поддержки tool calling и автоматического отключения инструментов нет. Текстового фолбэк-протокола нет. Clipboard Actions передаёт tools: [] и отвергает неожиданный tool call.

### 4.4 Метаданные моделей (Rev 4)

`ModelInfo` расширяется необязательными полями: тип (`chat` / `embedding` / неизвестно), загружена ли модель, максимум модели (contextLength), контекст загруженного экземпляра (loadedContextLength), поддержка tool calling. Поля заполняются только тем, что провайдер реально отдаёт; конкретные эндпоинты проверяются по документации установленных версий LM Studio и Ollama. Модели типа `embedding` не показываются в выборе чат-модели; при отсутствии типа — эвристика по имени (`embed`) с возможностью показать скрытые.

## 5. Инструменты

### 5.1 Протокол

```swift
protocol Tool {
    var name: String { get }
    var description: String { get }
    var parameterSchema: JSONSchema { get }
    static var baseRiskLevel: RiskLevel { get }
    static var isPolicyEnforceable: Bool { get }          // по умолчанию false (fail-closed), см. 6.6

    func riskLevel(for arguments: Arguments, context: ToolRiskContext) -> RiskAssessment // вычисление; инварианты проверяет ToolRiskEvaluator
    func execute(_ arguments: Arguments) async throws -> ToolResult
    func execute(_ arguments: Arguments, policy: SecurityPolicyEngine) async throws -> ToolResult
}
```

Точные имена в коде могут отличаться; источник истины — репозиторий, расхождения фиксируются в отчётах шагов.

### 5.2 Текущий набор

| Инструмент | Базовый уровень | Класс |
|---|---|---|
| `read_file` | safe | структурированный |
| `list_dir` | safe | структурированный |
| `search_files` | safe | структурированный |
| `write_file` | caution | структурированный |
| `move_file` | caution | структурированный |
| `delete_file` | dangerous | структурированный |
| `run_shell` | dangerous | универсальный |

`run_shell` выполняет `/bin/zsh -c`, таймаут по умолчанию 30 секунд, поддерживает отмену; возвращает stdout, stderr, код выхода и признак таймаута. Direct-режима, потокового вывода и рабочей директории нет. Правила по путям не действуют: единственная граница — подтверждение человеком каждого вызова. Начиная с v0.3.6 запуск через posix_spawn создаёт отдельную группу zsh и потомков. По таймауту, отмене и после завершения команды оставшаяся группа получает SIGTERM, до 2 с на завершение, затем SIGKILL. Чтение stdout/stderr неблокирующее, ожидание конца вывода после очистки ограничено 2 с; результат и аудит содержат пометки об остановленных фоновых процессах и усечении вывода из-за удерживаемого pipe. Инструмент не оставляет фоновые процессы в своей группе. Процессы, сами вышедшие из группы/сессии (демон, setsid/setpgid), этой очисткой не завершаются. SIGKILL не гарантирует немедленного завершения uninterruptible sleep; ожидание вызова всё равно ограничено.

В v0.4.7.1 каждый поток shell сохраняет первые 8 КиБ и последние 8 КиБ (кольцевой буфер); середина отбрасывается, чтение продолжается. При усечении результат содержит `[... N bytes omitted ...]` и `lifecycleNote` с фактически сохранёнными байтами отдельно для stdout/stderr. Границы UTF-8 выравниваются, некорректные байты заменяются. При превышении 32 МиБ любого потока группа завершается через SIGTERM/SIGKILL, добавляется необязательное `outputLimitExceeded: true`, инструмент и аудит сообщают failure / output limit exceeded. Для небольшого вывода JSON не меняется; лимиты задаются в ShellOutputLimits и внедряются в тестах.

`move_file` повышается до dangerous, если назначение существует по lstat (включая каталог и висячую ссылку), кроме тождественного объекта по device/inode. Причина: «Назначение существует: файл будет перезаписан». Сессионная память caution не разрешает такую перезапись.

## 6. Модель безопасности

### 6.1 Уровни риска

```swift
enum RiskLevel: Int, Comparable {
    case safe       // выполняется без подтверждения
    case caution    // подтверждение, допустима сессионная память
    case dangerous  // подтверждение всегда, память не применяется
}
```

**Определение уровня:** статичный базовый уровень объявляется инструментом; конкретный вызов может быть **повышен** на основании аргументов. Понижение невозможно ни при каких условиях.

`allowed_dirs` — отдельная настройка AppSettings.allowedDirectories в UserDefaults, по умолчанию пустая, с редактором в настройках. write_file и move_file вне этих директорий повышаются до dangerous; allow-правила сами по себе не расширяют allowed_dirs и не понижают риск. ToolRiskEvaluator обеспечивает max базового и вычисленного уровня и принудительный dangerous для универсальных инструментов.

Примеры повышения:
- `write_file` вне разрешённых путей → `dangerous`
- `delete_file` по пути с wildcard или на директорию → `dangerous`
- shell-команда в режиме `shell` (`/bin/zsh -c`) → всегда `dangerous` (существующий `run_shell`, см. 5.2)

### 6.2 Подтверждение

Карточка Approve/Reject в ленте чата, визуально различающаяся по уровню: цвет рамки и заголовка, для `dangerous` — аргументы всегда развёрнуты.

**Сессионная память** — только для `caution`. Сейчас общий на приложение `SessionPermissions` хранит в RAM Set<SessionPermission>, ключ — пара (toolName, riskLevel); действует до перезапуска или явного сброса в настройках, между беседами не разделяется. Повышение до dangerous исключает использование сохранённого caution-разрешения. **Rev 4:** область действия — одна беседа (а не всё приложение) до перезапуска приложения; форк беседы начинает с пустой памятью; смена рабочей папки проекта сбрасывает память всех его бесед. Для `dangerous` память недоступна.

### 6.3 Правила allow/block

Схема хранит четыре измерения. Сейчас принуждение включено только по `path` для шести файловых инструментов; остальные измерения всегда возвращают «нет решения». Планируемые фазы Rev 4:

| Измерение | Что описывает | Принуждение с |
|---|---|---|
| `path` | пути и глобы файловой системы | **v0.3** |
| `command` | regex-паттерны shell-команд | v0.6 (Shell) |
| `application` | bundle ID целевых приложений | v0.7 (AppleScript) |
| `host` | сетевые хосты | best effort, без гарантий |

```swift
@Model final class SecurityRule {
    var dimension: RuleDimension   // path | command | application | host
    var pattern: String
    var action: RuleAction         // allow | block
    var isEnabled: Bool
    var order: Int
    var isBuiltIn: Bool
    var ruleDescription: String
    var createdAt: Date
    var project: Project?          // Rev 4, ещё не реализовано
}
```

**Порядок разрешения:** включённые правила сортируются по `order`, затем `createdAt` и паттерну. Первое совпавшее block имеет безусловный приоритет над любым allow; порядок существенен между правилами одного действия. Разные измерения не конкурируют. При отсутствии совпадений — поведение по умолчанию для уровня риска. Allow не понижает риск.

Пути канонизируются с раскрытием `~`, существующих symlink и `..`; проверяются и исходный путь, и нормализованный аргумент инструмента. Совпадение с предком распространяется на потомков. Глобы поддерживают только `*`, `**`, `?`; List/Search фильтруют запрещённых потомков.

Редактор группирует правила по четырём измерениям, валидирует паттерны, сохраняет порядок перетаскивания и показывает решение всего набора на примере, включая несохранённый вариант. Встроенные правила можно только включать/выключать. Сброс с подтверждением восстанавливает все 16 встроенных правил и не меняет пользовательские. Набор загружается из SwiftData перед каждым вызовом; изменения действуют со следующего вызова без перезапуска.

**Про сетевые хосты — честно.** Статический анализ аргументов не может определить, куда пойдёт `npm install`, `git pull` или произвольный скрипт. Будущая проверка ограничится явными URL в аргументах; в v0.3.4 `host` только сохраняется. В UI это измерение помечается как неполное, чтобы не создавать ложного чувства защиты. Настоящее ограничение сети потребовало бы прокси или sandbox-профиля — вне текущего scope.

### 6.4 Sandbox-режим

**Не реализуется.** Списки правил — механизм фильтрации структурированных целей; граница применимости и роль подтверждения для универсальных инструментов описаны в 6.6. Отдельный режим со своей семантикой создавал бы вторую, конкурирующую модель разрешений, которую пришлось бы держать согласованной с первой.

### 6.5 Журнал аудита

Каждый вызов инструмента фиксируется независимо от исхода:

```swift
@Model final class AuditEntry {
    var timestamp: Date
    var toolName: String
    var argumentsJSON: String
    var riskLevel: RiskLevel    // вычисляемый; хранится riskRaw: Int
    var elevationReason: String?
    var decision: Decision     // вычисляемый; хранится decisionRaw: String
    var matchedRuleDescription: String?
    // Decision: approved | rejected | auto | blocked; userInitiated — Rev 4
    var outcome: Outcome       // success | failure | cancelled | notExecuted
    var resultSummary: String
    var errorDescription: String?
    var durationMilliseconds: Int?
    var conversationID: UUID?
    var checkpointID: UUID?       // Rev 4, ещё не реализовано
}
```

Хранение — SwiftData. Просмотр — отдельное окно с фильтрами по дате, инструменту, уровню и решению, с поиском по имени инструмента и аргументам. Экспорт — JSONL-файл на диск. Аргументы и summaries ограничены по длине, но не маскируются по содержимому; содержимое успешно прочитанных файлов в summary не копируется. Команды, write_file content и shell stdout/stderr могут содержать секреты. Срок хранения по умолчанию — 90 дней; доступны 30/90/365 дней или бессрочно, очистка старых записей при запуске; ручная очистка требует подтверждения.


`userInitiated` — будущий исход решения для действий пользователя из UI (например, откат); сейчас AuditDecision содержит только approved/rejected/auto/blocked.

### 6.6 Классы инструментов и граница применимости политик

Инструменты делятся на два класса по одному признаку: можно ли к их аргументам детерминированно применить политику безопасности.

**Структурированные** (`isPolicyEnforceable = true`). Аргументы типизированы, объекты воздействия (пути, хосты, bundle ID) извлекаются без интерпретации кода. Файловые инструменты, Native API. Действует вся модель: базовые уровни, повышение, allow/block-правила, сессионная память для `caution`.

**Универсальные** (`isPolicyEnforceable = false`). Аргумент — произвольный код или командная строка. `shell`-режим Shell-инструмента, AppleScript / Apple Events. Эффективный уровень всегда `dangerous`, сессионной памяти нет, карточка показывает полный текст; правила могут применяться только как дополнительный фильтр запрета и никогда не понижают уровень.

**Fail-closed по умолчанию.** Значение `isPolicyEnforceable` по умолчанию — `false`: новый инструмент без явной декларации считается универсальным. Принудительный `dangerous` для универсальных реализуется в той же неперекрываемой обёртке, что и инвариант неснижаемости.

**Direct-режим Shell** (`Process` с массивом аргументов) — открытый вопрос v0.6: исполняемый файл извлекается детерминированно, но семантика аргументов зависит от программы. Решается в разборе v0.6.

**Текущий `run_shell`.** Выполнение через `/bin/zsh -c`, таймаут по умолчанию 30 секунд, отмена, карточка и аудит уже реализованы. Правила по путям к нему не применяются: запрет `~/.ssh/**` не остановит `cat ~/.ssh/id_rsa`. В редакторе это постоянное предупреждение. Direct-режим пока отсутствует.

**Граница безопасности.** Sandbox-режима нет, поэтому allow/block-правила защищают от ошибок модели и неудачных формулировок, но не от скомпрометированной модели (prompt injection через содержимое файлов, буфера обмена, документов). Как только в реестре есть хотя бы один универсальный инструмент, правила по путям перестают быть границей: то же действие достижимо через `do shell script` или Finder. Границей безопасности в этом случае является подтверждение человеком каждого `dangerous`-вызова. Документация и интерфейс не должны обещать большего.

**Маршрутизация возможностей (требование к будущим инструментам).** Для каждой возможности существует один канонический инструмент. Файловые операции выполняются только файловыми инструментами. Описания Shell- и AppleScript-инструментов прямо указывают модели не использовать их для чтения, записи, перемещения и удаления файлов. AppleScript предназначен для управления приложениями: Mail, Calendar, специфичные для Finder действия (теги, Reveal, Корзина).

Начиная с v0.3.6 описание текущего `run_shell` прямо запрещает чтение, запись, перемещение, удаление файлов и просмотр каталогов через shell и направляет модель к read_file/write_file/move_file/delete_file/list_dir/search_files, поскольку shell обходит правила доступа к путям. Это мягкая мера маршрутизации, без парсинга команд и принуждения в runtime; она не является границей безопасности. Для будущего AppleScript требование сохраняется.

**AppleScript (v0.7), предварительные требования:**
- цели `tell application` проверяются по измерению `application`;
- наличие `do shell script` в скрипте дополнительно подчиняет вызов правилам измерения `command`;
- если цели скрипта извлечь не удалось, это отражается в причине уровня на карточке подтверждения.

### 6.7 Проект как периметр (Rev 4)

Беседа внутри проекта с заданной рабочей папкой работает в периметре:
- **allow** по измерению `path` = рабочая папка проекта (неявное правило) ∪ правила, привязанные к этому проекту; **глобальные allow-правила внутри проекта не действуют**, включая `allowed_dirs` (`AppSettings.allowedDirectories`); разрешённая зона = рабочая папка проекта ∪ allow-правила проекта;
- **block** = глобальные block-правила ∪ block-правила проекта; block по-прежнему приоритетнее;
- всё вне периметра — как «вне разрешённых путей» из v0.3 (повышение до `dangerous` или блокировка по действующему правилу);
- пути канонизируются тем же механизмом, что в v0.3 (разрешение симлинков, `..`), до сравнения.

Беседа без проекта и беседа в проекте без рабочей папки работают по глобальным правилам v0.3 — поведение не меняется.

Рабочая папка не может быть `/`; для домашней папки целиком и системных каталогов (`/System`, `/Library`, `/usr`, `/bin`, `/sbin`, `/private`) — предупреждение с явным подтверждением.

Встроенное неотключаемое block-правило защищает каталог данных приложения (`~/Library/Application Support/<bundle id>/`): защита применяется к файловым инструментам. Универсальный `run_shell` не соблюдает это правило и может читать и изменять базу, журнал и чекпоинты, если пользователь подтверждает команду (граница — 6.6). Реализовано в шаге 4.4: обязательные block-правила также защищают фактические файлы SwiftData (`~/Library/Application Support/default.store*`), plist настроек по bundle ID и `~/Library/LaunchAgents/**`. Хранилище не переносится. Подробности реализации и проверок — в `docs/step-4.4-report.md`.

### 6.8 Чекпоинты (Rev 4)

Реализовано в шаге 4.6 (`v0.4.6`): диффы/превью, fail-closed создание, откат отката,
хранение и точная связь аудита через `toolCallID`. Реализация, проверенная миграция
и ограничения описаны в [отчёте шага 4.6](step-4.6-report.md).

Перед выполнением одобренного или авто-разрешённого `write_file`, `move_file`, `delete_file` затрагиваемые файлы копируются в `~/Library/Application Support/<bundle id>/Checkpoints/<uuid>/` с манифестом (исходный путь, существовал ли файл, SHA-256, размер). Записывается `Checkpoint` и ссылка в `AuditEntry.checkpointID`.

- Лимиты: файл до 50 МБ, директория до 200 МБ суммарно; сверх лимита чекпоинт не создаётся.
- **Карточка подтверждения до решения пользователя показывает, будет ли возможен откат.** «Без возможности отката» — отдельная заметная пометка.
- Откат — действие пользователя из инспектора: подтверждение, снимок текущего состояния (откат сам откатываем), восстановление, запись аудита `userInitiated`.
- Хранение: по умолчанию до 2 ГБ и 30 дней; очистка при запуске и после создания чекпоинта; параметры в настройках.
- Чекпоинты не заменяют Git и бэкапы; это оговаривается в UI.

### 6.9 Видимость безопасности в UI (Rev 4)

UI должен явно показывать границу защиты: block каталога данных действует на файловые инструменты, но подтверждённый `run_shell` может читать и менять эти данные (6.6–6.7).

- Карточки подтверждения **никогда** не сворачиваются внутрь трейса выполнения.
- Свёрнутый трейс показывает в заголовке счётчики отклонённых, заблокированных и одобренных `dangerous`-шагов — свёртка не прячет инциденты.
- Чип политики в композере: действующий периметр, запомненные `caution`-разрешения беседы, сброс.
- Карточка записи показывает дифф; перемещение — откуда/куда и перезапись ли; удаление — сведения о файле и превью.
- Из пузыря питомца можно одобрить только `caution`, без запоминания; для `dangerous` доступна только кнопка «Открыть в чате».

## 13. Workspace и интерфейс (Rev 4, v0.4)

Источник идей — LM Studio Bionic (проекты и сессии, фоновые сессии, свёрнутый трейс, композер с чипами, инспектор); отличие — безопасность как видимая часть интерфейса.

### 13.1 Раскладка главного окна

`NavigationSplitView` + `.inspector`:
- **Сайдбар** — нативный `List` со стилем `.sidebar`. Секции «Проекты» (раскрываемые проекты с вложенными сессиями) и «Чаты» (беседы без проекта); архив скрыт за переключателем. У сессий — статус-иконки (13.3).
- **Центр** — лента сообщений и композер, ограниченные по ширине (~760 pt) и центрированные.
- **Инспектор** (правая панель, переключатель в тулбаре) — 13.5.

### 13.2 Проекты и сессии

`Project`: имя, рабочая папка (необязательно), инструкции (добавляются к системному промпту, до 4000 символов), порядок. Операции с беседой: закрепить, переименовать, переместить в проект, архивировать, удалить (с подтверждением), форк. Удаление проекта предлагает перенести его беседы в «Чаты» (по умолчанию) или удалить.

**Авто-заголовок.** После первого обмена — фоновый короткий запрос к той же модели без инструментов («заголовок в 3–5 слов»), очистка результата; при ошибке — обрезанное первое сообщение. Ручное переименование выставляет `titleIsManual`, после чего авто-заголовок не применяется.

### 13.3 SessionRunner и статусы

У каждой беседы — свой `SessionRunner` со статусом:

`idle` · `running` (генерация) · `toolRunning` (выполняется инструмент) · `needsApproval` · `ready` (завершено, не просмотрено) · `failed`

- Выполнение продолжается при переключении беседы и закрытии окна.
- `ready` выставляется, если беседа не открыта в момент завершения; сбрасывается при открытии (`hasUnreadResult`).
- Системные уведомления: о завершении — если беседа не на экране (настройка); о `needsApproval` — всегда при включённых уведомлениях.
- Агрегированный статус (приоритет `needsApproval` > `failed` > `running`/`toolRunning` > `ready` > `idle`) публикуется для питомца.

### 13.4 Лента

- **Трейс выполнения.** Шаги между сообщением пользователя и финальным ответом (вызовы, результаты, промежуточный текст) сворачиваются в строку «Работа: 2 мин 13 с · 5 шагов ›», во время выполнения — «Работает: 12 с · <текущий шаг>». В заголовке — счётчики инцидентов (6.9). Шаги внутри — с бейджами уровня риска.
- **Карточки подтверждения** — вне трейса, всегда видимы (6.9), с диффом и пометкой об откате (6.8).
- **Действия с сообщением** (по наведению): у ответа — копировать, форк; у запроса — повторить, копировать.
- **Форк** — новая беседа в том же проекте с историей до выбранного ответа включительно, заголовок «<заголовок> — ветка», пустая сессионная память.

### 13.5 Инспектор

Разделы: **Проект** (имя, рабочая папка, git-ветка из `.git/HEAD` без запуска процессов, «Изменить папку…»); **Файлы** (ленивое дерево рабочей папки, не более 500 элементов на уровень, открыть в Finder / Quick Look); **Безопасность сессии** (действующий периметр, запомненные `caution`-разрешения с отзывом, «Сбросить всё»); **Чекпоинты** (список с откатом); **Аудит** (последние записи беседы, ссылка на окно журнала с фильтром).

### 13.6 Композер

Многострочное поле (1–8 строк), Enter — отправить, Shift+Enter — перенос. Внутри рамки: чип политики (6.9), чип модели сессии, Send/Stop. Под композером: проект / git-ветка слева, «Контекст: X / Y» справа. Команда `/pet` перехватывается и переключает питомца, не уходя в модель. Элементы без реализованной функции в UI не добавляются.

**Модель сессии.** `Conversation.modelID` (nil — модель по умолчанию из настроек); смена применяется со следующего запроса.

**Счётчик контекста.** Использовано = токены запроса + ответа последнего обмена по событию `usage`; лимит — loadedContextLength загруженного экземпляра, иначе из настройки с пометкой «≈»; максимум модели — только в подсказке. Значение по умолчанию — 8192. Цвет: жёлтый от 70%, красный от 90% с подсказкой начать новую сессию или сделать форк. Автоматического сжатия истории нет.


#### Реализация 4.7: модель сессии и контекст

`Conversation.modelID` и `providerID` — необязательные поля с nil по умолчанию.
Провайдер определяется ключом секции `тип|нормализованный URL`, уже используемым
`DetectedProvider.id`; `ProviderEndpoint.id` использует тот же ключ.
Nil наследует глобальную настройку. Форк копирует оба поля. Меню чипа в общем
`ComposerView` обслуживает главное окно и popover; выбор недоступен во время прогона.
Раннер фиксирует провайдера, модель и поддержку инструментов в начале запроса;
автозаголовок получает тот же экземпляр провайдера. Явный `supportsTools == false`
отключает инструменты; nil сохраняет прежний набор.

`ChatStreamEvent.usage(promptTokens:completionTokens:)` разбирается из SSE usage
LM Studio (включая пустой choices) и финального NDJSON Ollama. Использовано —
сумма токенов последнего запроса, включая промежуточный запрос внутри AgentLoop;
перед каждым запросом usage сбрасывается, отсутствие данных отображается как «—».
Значение хранится в `Conversation.lastContextTokens`.

Лимит — `ModelInfo.loadedContextLength`: LM Studio native v1
`loaded_instances[].config.context_length`, Ollama `/api/ps.context_length`.
При нескольких экземплярах LM Studio берётся первый экземпляр из ответа.
Если данных нет, используется редактируемый `llm.defaultContextLimit` (8192),
с «≈» и пояснением. `contextLength` — максимум модели, только справочная подсказка,
никогда не лимит счётчика. Метаданные обновляются асинхронно при выборе беседы,
открытии меню и окончании прогона; каждый metadata-запрос имеет таймаут 1,5 секунды.
Пороги: обычный <70%, жёлтый ≥70%, красный ≥90% с предложением новой сессии/ветки.
Пустая беседа не показывает счётчик. Автоматического сокращения истории нет.


### 13.7 Пустое состояние

Иконка, название, одна строка статуса провайдера («LM Studio · <короткое имя модели>»), 3 подсказки-примера, заполняющие композер.

### 13.8 Настройки

Сцена `Settings`, вкладки: **Основные** (язык, уведомления, хоткей), **Модели** (провайдеры и эндпоинты, модель по умолчанию, лимит контекста по умолчанию), **Безопасность** (редактор правил из 3.4, журнал аудита, лимиты чекпоинтов), **Буфер обмена**, **Питомец**, **Внешний вид**. Содержимое — `Form` со стилем `.grouped`, выравнивание по верху.

- Выбор модели в списке обнаруженных применяется сразу; ручной эндпоинт — «Добавить эндпоинт…» в раскрывающейся секции. Один источник истины.
- Для каждого провайдера показывается статус, в том числе «не найден (localhost:11434)» с кнопкой «Проверить».
- Хост эндпоинта не loopback (`localhost`, `127.0.0.0/8`, `::1`) → предупреждение и явное подтверждение; частные сети (RFC 1918, `.local`) помечаются как LAN.

### 13.9 Локализация

Все пользовательские строки — String Catalog; русский и английский. По умолчанию язык системы, переопределение в «Основных» (применяется после перезапуска).

## 14. Десктоп-питомец (Rev 4, v0.4.x)

По мотивам Pets в десктоп-приложении ChatGPT: плавающий персонаж поверх окон как индикатор статуса агентных сессий.

### 14.1 Окно

`NSPanel`: `.nonactivatingPanel`, без рамки, прозрачный фон, уровень `.floating`, `canJoinAllSpaces` + `fullScreenAuxiliary`, не скрывается при деактивации приложения. Перетаскивается мышью, позиция сохраняется и при запуске возвращается в видимую область экрана. Включение: `/pet`, пункт menu bar, вкладка «Питомец».

### 14.2 Состояния и анимация

Строки спрайт-шита (контракт, порядок фиксирован):

| Строка | Состояние | Источник |
|---|---|---|
| 0 | `idle` | нет активных сессий |
| 1 | `running` | агрегат = running |
| 2 | `toolRunning` | агрегат = toolRunning |
| 3 | `needsApproval` | агрегат = needsApproval |
| 4 | `ready` | есть непросмотренный результат |
| 5 | `failed` | агрегат = failed |
| 6 | `drag` | панель перетаскивают |
| 7 | `sleep` | `idle` дольше 5 минут |

Рендер — кадры 64×64, масштаб ×1/×2/×3 (по умолчанию ×2), без интерполяции. Таймер кадров останавливается, когда панель скрыта. При reduce motion — кадр `reduceMotionFrame` каждой строки. Отсутствующая строка → `idle`.

### 14.3 Формат питомца

Папка с двумя файлами: `pet.json` и `spritesheet.png`.

```json
{
  "version": 1,
  "id": "bronya",
  "name": "Броня",
  "frameSize": 64,
  "columns": 8,
  "rows": [ { "row": 0, "state": "idle", "frames": 6, "fps": 6, "loop": true } ],
  "reduceMotionFrame": 0
}
```

Валидация (отказ целиком при нарушении): `version == 1`; `id` — `[a-z0-9-]{1,40}`; `name` до 40 символов; `frameSize == 64`; `columns` 1…16; состояния из известного набора, `idle` обязателен; `frames` 1…`columns`; `fps` 1…30; `spritesheet.png` — PNG по содержимому (не по расширению), ровно `columns×64` на `rows×64`, до 8 МБ. Прочие файлы игнорируются, код и скрипты не загружаются.

Встроенный питомец — «Броня» (броненосец-хранитель) в ресурсах бандла; до появления арта — программный плейсхолдер. Пользовательские питомцы импортируются через «Добавить питомца…» с копированием после валидации в `Application Support/<bundle id>/Pets/<id>/`.

### 14.4 Пузырь и Quick Chat

- Клик по питомцу → пузырь со списком активных и непросмотренных сессий со статусами; клик по сессии открывает её в главном окне.
- Для `needsApproval` уровня `caution` — Approve / Reject (без запоминания); для `dangerous` — только «Открыть в чате».
- Quick Chat: поле под питомцем, отправка в последнюю открытую сессию или в новую (переключатель, цель подписана).
- Настройка «Скрывать содержимое»: пузырь показывает только статусы без заголовков и текста.
- Настройка «Не дублировать уведомлениями о завершении, пока питомец на экране» (уведомления о `needsApproval` не подавляются).

## 15. Skills (Rev 4, v0.5, планируется)

Формат Agent Skills (`SKILL.md` + файлы). Детальный дизайн — в SPEC Rev 5 по итогам v0.4. Зафиксированные ограничения:

- Навык — недоверенный ввод: allowlist, SHA-256 содержимого в аудите, повторное подтверждение при изменении файла.
- Навык не меняет уровни риска и не создаёт правил.
- Источники: встроенная папка приложения; `~/.claude/skills` и `~/.codex/skills` — только по явному опт-ину.
- Скрипты из навыков не исполняются до v0.6 и затем только через Shell-инструмент по его правилам.
- Вызов через `@` в композере; «Создать навык из этой сессии».


## Приложение A. Соответствие имён (сверка v0.4.7)

Псевдокод SPEC сохраняет условные имена; фактические сигнатуры определяет код.

| SPEC | Код |
|---|---|
| AppState | общий ChatViewModel и AppSettings; отдельного AppState нет |
| ToolCallRecord | ToolCall |
| StreamEvent | ChatStreamEvent: contentDelta, toolCallDelta, usage, done; ошибки через throwing stream |
| ModelInfo | ModelInfo: id, kind, isLoaded, contextLength, loadedContextLength, supportsTools; DetectedProvider.availableModels: [ModelInfo] |
| LLMProvider.identifier | LLMProvider.name |
| LLMProvider.availableModels() | ProviderDiscovery.discover(); отдельного метода протокола нет |
| LLMProvider.stream(ChatRequest) | streamChat(messages:tools:); ChatRequest отсутствует |
| Tool.parameterSchema | Tool.parametersSchema |
| Tool.riskLevel(for:context:) | Tool.computeRisk(arguments:context:); инварианты — ToolRiskEvaluator.evaluate |
| Arguments | [String: Any] |
| ToolResult | ToolExecutionResult |
| Tool.execute(_:), execute(_:policy:) | execute(arguments:), execute(arguments:policy:) |
| Decision / Outcome | AuditDecision / AuditOutcome |
| AuditEntry.riskLevel / decision | вычисляемые свойства, хранимые riskRaw / decisionRaw |

RiskLevel, isPolicyEnforceable, SecurityRule, RuleDimension, RuleAction, AuditEntry, LLMProvider и Tool совпадают по именам. SessionRunner, Project, Checkpoint и usage реализованы; userInitiated — значение AuditDecision. SessionRunnerRegistry.aggregate готов для отображения статусов питомцем.
