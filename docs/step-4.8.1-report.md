# Шаг 4.8.1 — исправление фонового статуса и клика

## 1. Первопричины и воспроизведение

Пользователь уточнил: главное окно было закрыто. Ожидаемый конкретный статус, видимое состояние персонажа и источник запуска сессии не уточнены; эти детали не подменены предположениями.

**Владение состоянием.** На `v0.4.8` в `App/MacLMAgentApp.swift:15–18` модель/настройки/хоткеи хранились в `@State`, а контроллеры, контейнер и `SceneActions` — в обычных полях. В `init`, строки 54–66, создавались новый viewModel и новый SceneActions, которые напрямую получали PetController и MenuBarController. При пересоздании значения App SwiftUI сохраняет уже установленный State, а обычные поля получают новые ссылки. В результате главное окно может продолжать использовать прежнюю модель с активными сессиями, а новый питомец — другую модель с пустым реестром. Новый SceneActions также может ещё не иметь openMainWindowAction: она устанавливается только в onAppear главного окна. Это объясняет связь сбоя с закрытым окном.

Механизм retention воспроизведён в `PetNativeEventTests.testStateRetentionExplainsOldAppControllerMismatch`: при обновлении корневого SwiftUI view State сохраняет первый объект, а отдельно созданная ссылка уже указывает на второй. Это воспроизведение механизма жизненного цикла; точная последовательность действий пользователя с пересозданием App отдельно не записана.

**Нативный клик.** На `v0.4.8` `Pet/PetPanel.swift:50–53` всегда возвращал nil из hitTest и не задавал acceptsFirstMouse/передачу mouse events в панель. Кроме того, строки 20–28 брали глобальный NSEvent.mouseLocation вместо координат конкретного события. Регрессионный тест через NSPanel.sendEvent на отдельной копии тега v0.4.8 воспроизвёл отсутствие открытия окна и неправильную обработку порога drag. На исправленной версии он проходит.

**Что исправлять не требовалось.** Подписка PetController.observe читает aggregate внутри withObservationTracking и повторно регистрируется; чтение статусов раннеров отслеживается. Тест с реальным SessionRunnerRegistry/SessionRunner и фиктивными provider/tool на исходном v0.4.8 успешно прошёл running → needsApproval → toolRunning → ready → failed. При одном корректно связанном экземпляре подписка работает даже без взаимодействия с UI. Поэтому реестр, AgentLoop и разрешения не менялись.

**Почему тесты 4.8 пропустили дефект.** Контроллер создавался однократно, без восстановления SwiftUI State с новыми controller references. Клик проверялся прямым вызовом panel.onClick, обходя hit testing, first mouse, mouseDown/Dragged/Up и native event dispatch. Таблица статусов проверялась преимущественно как чистая функция.

## 2. Минимальное исправление

- Имеющаяся сборка зависимостей перенесена из инициализатора значения App в `App/ApplicationRuntime.swift`. `SessionApplicationDelegate.runtime` — lazy singleton для этого экземпляра делегата приложения, не глобальная статическая переменная. Создание контейнера, настройки, инструменты, защита данных и зависимости сохранены.
- Главное окно, settings, menu bar/popover, уведомления и PetController получают один runtime, один ChatViewModel/SessionRunnerRegistry и один SceneActions. Закрытие окна не уничтожает эти зависимости и не требует повторного onAppear для повторной регистрации действий нового объекта.
- PetHostingView остаётся неклавиатурным, принимает first mouse, возвращает себя как hit target и явно передаёт мышь PetPanel. Панель по-прежнему не становится key/main.
- Порог drag остаётся 3 pt. Расстояние вычисляется по locationInWindow события, переведённому в экранные координаты, а не по состоянию глобального курсора.
- Доступ к внутреннему PetRuntime в пределах модуля открыт для прямой проверки состояния вместо reflection; пользовательского API/функций не добавлено.

Изменения ограничены жизненным циклом существующих зависимостей и доставкой мыши. Пузырь, импорт и другие функции не добавлены. Новых зависимостей, пользовательских строк и сетевого кода нет. Новая provider-фикстура использует URLProtocol, исключающий сетевой транспорт discovery. Рабочее SwiftData-хранилище не открывается: тесты используют in-memory контейнеры и отдельные UserDefaults suite.

Localizable.xcstrings не редактировался вручную и не включён в коммит: существующие форматирование/extraction metadata остаются незакоммиченными.

## Проверки

- Реальный реестр и реальные SessionRunner с фиктивными provider/tool: running, needsApproval, toolRunning, ready, failed; выбранная другая беседа; панель скрыта; никаких ручных UI-триггеров обновления.
- Реальный aggregate: failed имеет приоритет над running/ready, needsApproval — над failed; клик выбирает нужную беседу и вызывает SceneActions.
- NSPanel.sendEvent: смещение 2 pt открывает окно, смещение ровно 3 pt вызывает drag без открытия; key/main не меняются.
- SwiftUI State retention: воспроизведение расхождения старой схемы владения.
- Полный `make test`: 250 тестов, один штатно пропущен, ноль ошибок.
- `make lint`: ноль нарушений в 141 Swift-файле. Debug собирается в составе тестового запуска.

Коммит: `fix(pet): reflect live session status and open conversation on click`. Локальный тег: `v0.4.8.1`. Push и публикация релиза не выполнялись.

## 3. Ручная проверка

1. Запустить именно новую сборку. В первой беседе запустить генерацию, выбрать другую и закрыть главное окно. Питомец должен показывать running и toolRunning; после завершения — ready.
2. При закрытом окне вызвать caution/dangerous-подтверждение из фоновой беседы: питомец показывает needsApproval; короткий клик открывает эту беседу с обычной карточкой подтверждения. Подтверждения из питомца не добавлены.
3. Проверить failed и конкурирующие сессии: needsApproval > failed > toolRunning > running > ready > idle; клик открывает соответствующую беседу.
4. Из popover строки меню запустить сессию, закрыть popover и главное окно; повторить проверку статуса и клика.
5. Проверить короткий клик с небольшим движением и полноценное перетаскивание: drag не должен открывать главное окно и не должен забирать клавиатурный фокус.

Нативный dispatch проверен автоматизированно. Полный ручной повтор пользовательского сценария с локальной LLM и реальным закрытием главного окна в этом запуске не выполнялся.
