# Шаг 4.5 — свёрнутый трейс, действия с сообщениями, форк

Версия: `v0.4.5`. Изменения ограничены этим шагом; схема SwiftData,
`AgentLoop`, `SessionPermissions` и движок безопасности не изменены.

## 1. Хранение и счётчики

Ход начинается с `Message(role: .user)`. Каждая итерация модели создаёт
`Message(role: .assistant)`; текст и массив `ToolCall` могут находиться в одном
сообщении. У вызова есть UUID записи/подтверждения, отдельный `providerCallID`,
аргументы, статус, timestamp и необязательный снимок риска. Результат сохраняется
в `ToolCall.resultJSON` (представление для человека) и отдельном `.tool`-сообщении
(исходный текст для модели, связь через `toolCallID == providerCallID`).
Для shell трейс читает исходный JSON из `.tool`, отдельно показывает exitCode,
timedOut и lifecycleNote, а stdout/stderr ограничивает первыми 20 строками.
В ленте результат не дублируется отдельным сообщением.

Ожидающие вызовы сохраняются до решения. После решения статус временно approved
или rejected; после выполнения — completed/failed. При отмене незавершённые
сохранённые вызовы получают rejected и `Cancelled by user`, плюс `.tool`-ответ.
Не все ещё не выполненные вызовы пакета обязательно уже представлены ToolCall.

Счётчики:

- Reject: решение rejected из аудита либо статус rejected; заполнители
  `Cancelled by user` не считаются самостоятельным Reject.
- Блокировка правилом: `AuditEntry.decision == blocked`.
- Одобрено dangerous: решение approved и снимок dangerous из аудита;
  completed/failed сами по себе не являются доказательством одобрения.
- Ошибка инструмента: статус failed, исключая подтверждённую аудитом блокировку.

Аудит выбирается по conversationID и интервалу хода. UUID аудита **не совпадает**
с UUID подтверждения. Записи сопоставляются по имени, санитизированным аргументам,
времени начала сообщения и порядку исполнения; каждая запись используется один раз.
При повторе записи до нового сообщения ассистента исключаются из сопоставления.
Снимки риска для вызовов без карточки подтверждения заполняются из уже созданного
аудита в SessionRunner; UI только отображает их.

**Ограничение существующей схемы:** после удаления аудита или в форке, где по
заданию нет копий AuditEntry, невозможно восстановить точные блокировки и
одобрения dangerous. Эти счётчики показывают только подтверждённые аудитом данные;
failed без аудита учитывается как ошибка. Не добавлены скрытые записи аудита или
поля модели ради восстановления недостающих решений.

## 2. Граница финального ответа

Чистая функция `RunTraceGrouping.group` получает хронологический массив.
Сообщение с вызовами всегда принадлежит прогону, включая его текст. Только
последнее сообщение ассистента без вызовов считается финальным после завершения.
Более ранний текст без вызовов остаётся промежуточным шагом. Во время генерации
текущий ответ без вызовов отображается отдельно, без действия «Ветка».
Пустой прогон не рисуется.

SessionRunner хранит окончания отдельных ходов в RAM: отмена/ошибка не превращаются
в финальный ответ при последующем запросе или переключении бесед. Ошибки также
распознаются по существующему сохранённому сообщению `Ошибка: …`.
После перезапуска отменённый частичный ответ без сохранённого маркера отмены
неотличим от финального: существующая схема не хранит признак завершения хода.

Новые финальные ответы получают timestamp окончания, поэтому длительность —
разница между timestamp запроса и ответа. Ранее timestamps создавались при старте
ответа и сдвигались на микросекунды между итерациями. Старые длительности исправить
достоверно без дополнительной истории нельзя. Для остановленных новых ходов
используется время окончания из RAM, затем данные аудита/сообщений как fallback.

## 3. Производительность

Группировка кэшируется в ChatView и пересчитывается при изменениях сообщений,
статусов вызовов или состояния раннера, а не внутри построения каждой строки.
Лента использует LazyVStack. Завершённые прогоны по умолчанию свёрнуты;
раскрытие хранится в ChatViewModel по UUID пользовательского сообщения на время
работы приложения. TimelineView обновляет только активный заголовок раз в секунду.
Счётчики пересчитываются при изменении вызовов/аудита, а не каждый тик таймера.

XCTest measure: 400 сообщений / 100 ходов / 300 вызовов, десять повторений:
среднее около **2 мс** (зафиксированный замер 1.21–3.04 мс, Debug, Apple Silicon).
Это замер группировки, не FPS или полная профилировка AppKit/SwiftUI.

## 4. Подтверждения и действия

`TraceTurn.pendingCalls` существует независимо от `expandedSteps(isExpanded:)`.
Тест проверяет: свёрнутые шаги пусты, раскрытые содержат сообщение, ожидающая
карточка присутствует в обоих состояниях. После решения pendingCalls пуст,
вызов остаётся шагом. В RunTraceView карточки расположены под заголовком,
отдельным соседним блоком перед условием раскрытия. Группировка выполняется
при выборе беседы, включая фоновую с ожидающим подтверждением.
Содержимое ConfirmationCard не менялось. Ручная проверка кликами/VoiceOver
и скриншотами не выполнялась.

Повтор подтверждается alert с предупреждением о файловых действиях. SessionRunner
оставляет исходное пользовательское сообщение, удаляет только последующие
сообщения с каскадом ToolCall, сохраняет аудит и память разрешений и начинает
генерацию на сохранённой истории. Запрещён при выполнении/ожидающих подтверждениях.
Форк копирует сообщения и вызовы с новыми UUID, сохраняет проект, статусы и снимки
риска, устанавливает ручной заголовок и сбрасывает флаги. Исходная беседа независима;
новых AuditEntry и запуска генерации нет. Новая беседа выбирается и открывается
в главном окне. Копирование сохраняет исходный markdown в NSPasteboard.
Действия доступны по наведению и в контекстном меню.
