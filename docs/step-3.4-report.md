Реализован только шаг 3.4. Фаза v0.3 завершена с тегом `v0.3.4`; следующая фаза не активирована.

## Реализация и проверка

- Четыре группы в существующей вкладке безопасности; allowed_dirs и сессионные разрешения сохранены.
- Постоянный текст о неприменимости правил к run_shell с примером `cat ~/.ssh/id_rsa`.
- CRUD пользовательских правил, переключатели всех правил, перетаскивание внутри группы. Встроенные правила защищены на уровне UI и store: только isEnabled изменяемо.
- Валидация: глобы соответствуют реальному matcher (*, **, ?), regex компилируется Foundation, позиция ошибки получена публичным ICU API, bundle ID и hostname/wildcard проверяются по формату. Пустые паттерны запрещены.
- Канонический путь, предупреждение о широких паттернах; preview использует весь набор и несохранённый вариант. Для path вызывается тот же decision(for:tool,arguments:), что для read_file; disabled pattern может совпасть, но не влияет на решение.
- Сброс с подтверждением восстанавливает все 16 встроенных правил, их состояние, описание и порядок. Пользовательские объекты и значения сохраняются.
- `make test`: 131 тест, 0 ошибок. Семь новых тестов охватывают защиту встроенных правил, reset, порядок, валидацию, preview и обновление в одном AgentLoop и между разными ModelContext.
- `make build`: успешно. Debug-приложение запущено через LaunchServices, процесс продолжает работать. Интерактивный обход всех элементов UI и drag-and-drop вручную не выполнялся.
- SwiftLint: новый код без замечаний; общий strict lint не проходит из-за 45 существующих нарушений в других файлах. Они не исправлялись вне scope.

## 1. Мгновенное применение

SecurityPolicyEngine содержит неизменяемый снимок для одного вызова, но AgentLoop создаёт его заново и вызывает securityRules() перед каждым инструментом. В приложении closure читает SwiftData через policyContext; редактор сохраняет в своём ModelContext. Регрессионный тест проверяет именно отдельные контексты, включая уже загруженные объекты. Инвалидация не потребовалась. Уже начавшийся вызов, включая ожидающий подтверждения, использует исходный снимок; требование относится к следующему вызову.

## 3. Готовность к полноценному Shell v0.6

Уже готовы Process, `/bin/zsh -c`, параллельное чтение stdout/stderr, exitCode, таймаут 30 секунд, отмена, обязательное dangerous-подтверждение, аудит, схема хранения command-правил и regex-редактор. Потоки сейчас читаются до EOF, а результат показывается после завершения.

Нужно достроить:

- Два явных режима и схему аргументов: direct с executable + argv без интерпретации оболочкой; shell с точной командной строкой.
- Разрешение/канонизацию исполняемого файла, определение семантики PATH и объекта проверки command. Из direct-аргументов нельзя универсально вывести все побочные действия программы.
- Принуждение command: runtime сейчас возвращает noDecision; для универсальных инструментов требуется отдельный фильтр, не открывающий им path-policy и не понижающий dangerous.
- Рабочую директорию: валидацию, отображение на карточке, передачу в Process.currentDirectoryURL и запись в аудит.
- Потоковые события stdout/stderr в интерфейс, ограничение объёма, backpressure и корректное завершение при отмене.
- Завершение дерева процессов/process group и конечные сроки ожидания EOF. Текущий kill адресован процессу zsh; потомки могут продолжить работу и удерживать pipe.
- Контракт маршрутизации файловых операций и целевые тесты безопасности direct/shell, command priority, timeout/cancellation.

## 4. Ограничения вне scope

- Универсальный shell обходит path-блокировки; prompt injection может склонить пользователя подтвердить опасную команду. OS sandbox отсутствует.
- Между проверкой пути и файловой операцией остаётся TOCTOU; также изменение правил во время ожидающего подтверждения вызова не перепроверяется перед исполнением.
- Сессионный caution запоминается для инструмента, а не конкретного пути/операции.
- Аудит сохраняет аргументы (включая write_file content) и shell stdout/stderr с ограничением длины, но без маскирования секретов. Сам журнал не защищён от действий разрешённого shell.
- command/application/host пока не принуждаются; host не сможет ограничивать произвольные сетевые действия статическим анализом.
- Защита isBuiltIn обеспечена редактором/store, а не запретом изменения локальной базы сторонним процессом.
