# Шаг 4.3 — SessionRunner и фоновые сессии

Дата: 2026-10-05. Исходное состояние: `v0.4.2`. Результат: `v0.4.3`.

1. **Перенос и безопасность.** После согласования плана оркестрация перенесена
   из `ChatViewModel` в `@MainActor @Observable SessionRunner`: запрос,
   стриминг, Message/ToolCall, подтверждения, отмена и запуск AutoTitleService.
   Реестр создаёт раннеры лениво по UUID беседы и удерживает их независимо от UI.
   ChatViewModel управляет выбором, черновиком и операциями рабочего пространства;
   его прежние методы Send/Stop/подтверждения теперь делегируют выбранному раннеру.
   Представления сохраняют прежнюю ленту и карточки. SystemPromptBuilder,
   AutoTitleService и ограничение восьми итераций используются как раньше.

   Общий AgentLoop непригоден для конкуренции: у него `isGenerating`,
   `pendingConfirmations` и ConfirmationCoordinator. `independentRun()` создаёт
   отдельный актор и координатор с тем же реестром инструментов, SessionPermissions
   и замыканиями правил, контекста риска и аудита. Добавлено событие
   `toolExecutionStarted`, после публикации которого проверяется отмена перед
   исполнением. Алгоритм оценки риска, правил и запоминания разрешений сохранён.
   **До 4.4 запомненное caution-разрешение действует между беседами.**

   UUID подтверждения сохраняется как ToolCall.id. Раннер проверяет UUID беседы,
   активного assistant-сообщения и pending-статус перед отправкой решения своему
   координатору. Одинаковые providerCallID разных бесед не смешиваются.
   Отмена сохраняет частичный текст, завершает карточки и сохраняет аудит.
   Удаление/архивация ждут выхода нужного цикла; удаление проекта — всех его
   циклов. Пересекающиеся удаления защищены от повторного доступа к удалённым
   SwiftData-объектам. На выходе NSApplicationDelegate возвращает terminateLater,
   отменяет все раннеры/авто-заголовки и отвечает после завершения задач.

   Добавлено только поле Conversation.hasUnreadResult с default false.
   Независимая миграция сохранённой копии реального store v0.4.2 прошла:
   9 бесед, 58 сообщений, 20 ToolCall. Все прежние поля и связи совпали в семи
   таблицах; новое поле false. Снимки и сравнение остаются локально в
   `build/step43-validation/`, вне Git, снимки с правами 0600.
   Отклонение: первый XCTest host после переноса уже открыл обычный store до
   добавления изоляции. Данные не удалялись/не заменялись. Последующие XCTest host
   и нативный smoke test используют хранилище в памяти; migration test каждый раз
   открывает новую временную копию. Время изменения обычного store после изоляции
   осталось 20:53:02, последующие проверки его не изменяли.

2. **Конкуренция провайдеров.** Два одновременных HTTP/SSE-прогона на локальном
   LM Studio, модель `google/gemma-4-e4b`, одинаковый синтетический запрос,
   max_tokens=250: первое SSE-событие через 1,052/0,983 с; полное время
   6,715/6,640 с; по 248 SSE-событий; ошибок нет. Одиночный контроль:
   первое SSE-событие 0,436 с, полное время 5,561 с, 249 событий. Полное время
   параллельного ответа в этом замере больше примерно на 19–21%.
   Потоки перекрывались:
   строгой последовательной очереди целых ответов в этой конфигурации не было.
   Это измерение конкретной модели/настроек, не гарантия для любых моделей.
   Нативный UI также проверен с двумя активными беседами на этом провайдере.
   Ollama на localhost:11434 не отвечает (connection refused); очередь/скорость
   Ollama не проверены. Число раннеров не ограничивается приложением. Пользователю:
   параллельные сессии увеличивают нагрузку/потребление памяти и могут ждать
   сервер или замедляться; настройки конкуренции остаются на стороне провайдера.

3. **Menu bar и жизненный цикл.** Popover и главное окно используют один
   ChatViewModel, выбор беседы и реестр. Send/Stop относятся к текущей беседе
   независимо от места нажатия. Закрытие popover/главного окна не отменяет задачи.
   На ad-hoc Release сборке с store в памяти через нативный UI проверены:
   переключение во время генерации, две активные беседы, Stop выбранной при
   продолжении другой, unread-индикатор и сброс при выборе, закрытие/повторное
   открытие главного окна с продолжающейся генерацией, штатный Quit.
   Процесс завершился с кодом 0. Отмена группы процессов run_shell покрыта
   существующими ShellProcessTests; отмена всех раннеров — новым тестом реестра.

4. **Контракт для 4.8.**

   ```swift
   @MainActor @Observable final class SessionRunnerRegistry {
       private(set) var runners: [UUID: SessionRunner]
       var aggregate: AggregateStatus { get }
       func runner(for conversation: Conversation) -> SessionRunner
       func cancelAllAndWait() async
   }
   struct AggregateStatus: Equatable {
       enum Kind: Equatable {
           case needsApproval, failed, toolRunning, running, ready, idle
       }
       let kind: Kind
       let needsApproval, failed, toolRunning, running, ready, idle: [UUID]
   }
   ```

   Списки UUID отсортированы детерминированно. Приоритет:
   needsApproval > failed > toolRunning > running > ready > idle.
   ready учитывает persisted unread даже без созданного раннера; статус ошибки
   сохраняется до следующей отправки. Отмена возвращает idle и не создаёт unread.
   Проверены все 32 комбинации основных статусов с/без unread, пустой агрегат,
   фоновые результаты и сброс при выборе. Уточнение SPEC: ready — состояние
   агрегата и persisted-флаг, отдельного case ready в SessionStatus нет;
   toolRunning приоритетнее running, как требует задание 4.3.

5. **Уведомления.** UNUserNotificationCenter получает только заголовок,
   «Готово»/«Ошибка»/название инструмента и UUID беседы; аргументы не передаются.
   Оба переключателя включены по умолчанию. Разрешение не запрашивается на запуске
   или при событии: запрос вызывается при переходе переключателя false → true
   либо кнопкой «Разрешить уведомления…» (для первоначальных defaults=true).
   Видимость требует выбранной беседы, открытого неминимизированного главного
   окна, key-window и активного приложения. Фоновое подтверждение и завершение
   уведомляют при соответствующей включённой настройке.

   Release собрана и подписана ad-hoc; codesign verify прошёл. Отдельный ad-hoc
   probe с bundle ID local.maclm-agent получил authorization=0 (notDetermined),
   alert=0 (notSupported). При таком состоянии приложение не отправляет баннеры.
   **Реальный показ баннера и физический клик не проверены**; ad-hoc совместимость
   доставки этим результатом не доказана. Обход текущего состояния: в «Основные»
   нажать «Разрешить уведомления…» и согласиться в macOS, затем при необходимости
   включить баннеры в системных настройках уведомлений. Если macOS отвергает
   ad-hoc identity, следующая проверка — установленная сборка со стабильной
   подписью Developer ID. Формирование payload и маршрут клика (выбор беседы,
   сброс unread, открытие главного окна, отсутствующий UUID) покрыты unit-тестами.
   **Название беседы присутствует в уведомлении и может быть видно на
   заблокированном экране** согласно системным настройкам preview.

6. **Главный поток и проверки.** SwiftData остаётся на главном акторе,
   сеть/инструменты — существующие async провайдеры и AgentLoop actor.
   Нагрузочный тест: два одновременных прогона по 1000 дельт без pacing,
   дисковый SwiftData, контроль главного актора каждые 5 мс. Прогоны заняли
   около 1 с; наблюдаемые максимальные интервалы heartbeat 7,6–9,0 мс.
   Все 2000 дельт сохранены, проверены повторным чтением другим ModelContext.
   В нативном UI деградации при двух потоках не наблюдалось. Батчи не добавлены:
   на измеренном сценарии основания менять прежнюю семантику сохранения отсутствуют.
   Это heartbeat главного актора, не инструментальное измерение FPS.

   До переноса прошёл весь исходный набор с новыми проверками истории двух вызовов
   и ошибки провайдера. Дополнительная завершённая approve/reject-регрессия затем
   отдельно проверена на изолированной сборке исходного тега v0.4.2: 33 теста
   (SessionRegression, Composer, Workspace, AuditLog), без ошибок. Тестовый host
   этой сборки принудительно использовал память. После переноса проходят все
   178 тестов без ошибок, включая новые проверки одновременных подтверждений/отмены, агрегата,
   unread, shutdown, пересекающихся удалений, payload/маршрута уведомлений,
   нагрузочный тест и полноту ru/en каталога.
   Общий make lint не проходит: нарушения форматирования воспроизводятся уже на
   v0.4.2. Новые Session-файлы, MainWindowView и ChatViewModel проверены SwiftLint
   без нарушений; массовое форматирование чужих файлов в шаг не включено.
